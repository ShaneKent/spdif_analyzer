# Codec metadata and integrity

Version 0.3 adds bounded inspection of received AC3, EAC3 and DTS core frames. It does not decompress audio. Transport declarations, common codec-header syntax, declared frame extent, and CRC results are separate evidence.

| Format | Metadata and packing | CRC checks |
| --- | --- | --- |
| AC3, BSID 0–8 | 16-bit BE/LE; sample rate, channel configuration, LFE, nominal bitrate, frame bytes/samples | CRC1 first 5/8 region; full frame excluding sync |
| EAC3, BSID 11–16 | 16-bit BE/LE; individual stream type/ID, block count, dependent channel map, per-frame derived bitrate | Full frame excluding sync |
| DTS core | 16-bit and 14-bit BE/LE; base-band rate, core channels, target bitrate, physical/logical sizes, block/termination/extension flags | HCRC absent or not checked as specified; full codec CRC unsupported |

Unsupported revisions remain explicit, with any safely parsed raw codes retained. Channel counts describe a frame/substream; extension channels and a complete EAC3 presentation are not inferred without association evidence. Logical DTS frame bytes and physical 14-bit packed bytes differ.

Integrity states are not_applicable, not_checked, absent, unsupported, truncated, failed, and passed. A passed structure check covers the inspected common header and declared physical extent, not complete compressed-body syntax or audible output. A passing CRC is error-detection evidence; it does not replace transport validity or prove valid audio. DTS HCRC is not silently treated as passed: the referenced specification says to extract it when present without applying its CRC test.

Codec_frame structured/JSONL records contain codec/packing, rate/channels/bitrate, frame sizes, raw codes, check states, contradictions and original transport Pc/Pd/source coverage. Byte offsets and frame indices associate multiple frames with a burst. Coverage denotes the whole transport words covering a frame, not an invented midword boundary. Source_interval_known distinguishes established intervals. Invalid/truncated remainders stop inspection; no search for a later sync word or Pa/Pb invents an extent.

In Logic select **Export output → Codec frames JSONL** for the retained snapshot records. Codec metadata also appears in structured table notifications. Burst-extraction indexes add codec_frame entries with a nested versioned record; burst entries continue to describe transport acceptance. Transport-complete payload extraction remains possible when a codec check fails or is unsupported, with that distinction recorded. Existing raw payload bytes are unchanged. Live SDK snapshots do not invent EOF; explicit offline EOF can report partial codec input.

## Professional channel-status CRCC

AES3 Annex B CRCC is evaluated separately from subframe parity and declared status-field reliability. Received and expected CRC bytes are exposed in status JSON, structured rows and appended status CSV columns. Proven bad CRCC disables status-derived PCM/layout trust, resets semantic comparison baselines, and cannot be bypassed by a WAV rate/precision override. Health retains parity-based status counts and adds separate passed/failed/unverified CRC counts.

Minimum AES3 implementations can transmit zero instead of a generated CRCC. A matching calculated zero passes; a nonmatching zero on a pure minimum block is absent, and an extended zero block is not_checked because an unimplemented check and a damaged zero cannot be distinguished from those bits alone. Compatibility with parity-good supported minimum status is retained without claiming CRC verification. A nonzero mismatch is failed.

The two published Annex B examples are literal test vectors: bytes 0/1/4 = 3D/02/02 produce 9B; byte 0 = 01 with remaining bytes zero produces 32. Tests cover bit corruption, valid zero, minimum fallback, per-channel attribution, trust recovery and override rejection.

## Primary references and verification

- [AES3-1992 (r1997), Annex B and §5.2](https://cim.mcgill.ca/~jer/courses/comparch/assignments/03/as1/aes3-1992.pdf): CRCC examples and minimum implementation.
- [ETSI TS 102 366 v1.4.1](https://www.etsi.org/deliver/etsi_ts/102300_102399/102366/01.04.01_60/ts_102366v010401p.pdf): AC3/EAC3 syntax and CRC coverage.
- [ETSI TS 102 114 v1.5.1](https://www.etsi.org/deliver/etsi_ts/102100_102199/102114/01.05.01_60/ts_102114v010501p.pdf): DTS core syntax/HCRC handling.
- [Earlier DTS packing description](https://www.etsi.org/deliver/etsi_ts/102100_102199/102114/01.02.01_60/ts_102114v010201p.pdf), [libdcadec implementation](https://github.com/foo86/dcadec/blob/master/libdcadec/dca_frame.c): packed-word boundary interoperability.

The independent codec tests embed complete frames generated by FFmpeg and compare metadata/CRC behavior against its parser/decoder, including corrupted regions and truncations. The runtime parser has no FFmpeg dependency. Independent published CRC examples prevent an encoder/decoder pair from silently sharing the same assumption.
